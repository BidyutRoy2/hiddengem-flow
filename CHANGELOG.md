- **NEW: in-extension update checker (finding A-06, verified live).** An unpacked extension never auto-updates — Chrome has no self-update API and no extension can replace its own files — so the checker only *notices* a newer build and points at the manual replace-files + Reload steps; no copy claims otherwise. New `entrypoints/shared/updates.ts`: `BUILD_DATE` (ISO constant, hand-updated on every release build — the checker compares it against the release asset's `updated_at`), a small semver compare (leading `v` stripped, `-suffix` counts as older than the same plain version), and `checkForUpdates()` — GET `https://api.github.com/repos/BidyutRoy2/hiddengem-flow/releases` (public, no auth, at most once per 6 h, far under the 60/hr/IP limit), first entry wins (prerelease included — the dev pre-release IS the channel). An update is available when the zip asset's `updated_at` (else the release `published_at`) is newer than `BUILD_DATE`, or the tag is a later semver than the manifest version. Stored under new key `hiddengemflow.update.v1` (`{ tag, publishedAt, assetUpdatedAt, downloadUrl, checkedAt, available, dismissedTag, dismissedAssetUpdatedAt, retryAfter }`); a 403/network failure fails silently with a 1 h backoff. No new permissions, no `chrome.alarms` (deliberately removed in A-02 — not re-added). The background checks on startup/install and on `MSG_CHECK_UPDATES` (dashboard ask; Settings forces it); the dashboard checks on open only if 6 h passed since `checkedAt`. **Where it shows:** Dashboard Overview banner with the exact honest wording + **Download the new build** (a real link to the release page), **How to update** (the replace + Reload steps) and **Dismiss** (keyed by tag + assetUpdatedAt — a newer asset re-shows the banner); floating windows (in-page + standalone popup) show one compact line, \"Update available: \<tag\> — open the Dashboard to download it.\"; Settings has a **Check for updates** button + \"Last checked\" + a network-behaviour line documenting the api.github.com contact. - **FIX: `GM_notification` now actually shows the notification (finding A-04, verified live).** In Chrome 158's `chrome.userScripts` USER_SCRIPT world the ONLY chrome API is `chrome.runtime.id` — `chrome.runtime.sendMessage`, `chrome.storage`, `chrome.tabs` are all `undefined` (verified live with a 23-path capability probe), so the old shim silently did nothing and the background handler never fired: the store script "Markdown Link Copier" copied fine but no notification ever appeared. `chrome.storage` as a signal transport was ruled out the same way — it is `undefined` in that world too. The fix adds no permission: the shim still tries `sendMessage` first when it exists, otherwise appends a transient signal node (`[data-hgf-gm-notify]`, unique id + title/message) to the page DOM, and a new relay content script (`public/gm-relay.js`, ISOLATED world) — runtime-registered by the background via `chrome.scripting.registerContentScripts` for exactly the `@match` patterns of enabled scripts — drains the node (initial scan + MutationObserver) and forwards it with `sendMessage`. A `BroadcastChannel` was deliberately NOT used (origin-scoped across tabs: one tab's signal would be forwarded by every other tab on the same origin). The background dedupes by notification id (in-memory, capped at 200) and re-attempts relay registration on startup, on script register/enable, and on `chrome.permissions.onAdded`. Live test 2026-11-15: Markdown Link Copier installed from the live store, "⧉ Copy link" clicked on example.com → notification appears with the right title/message, clipboard still gets `[Example Domain](https://example.com/)`; GM_setValue/GM_getValue round-trip still works.

## 1.0.2 — Standalone floating window: works with no website open (2026-11-15)

- **FIX (user report, real bug): the toolbar click did nothing when no website was open.** The floating window is a content script injected into the active tab, and Chrome forbids injection on `chrome://`, `brave://`, the Web Store, `about:blank` and new-tab pages — so clicking the icon on a Brave new tab page (the user's screenshot) silently did nothing. Fix (`entrypoints/float/` new, `entrypoints/background.ts`): a standalone floating page (`float.html`, same UI as the in-page window — header + gem logo, Daily Tasks with Open All, Active Scripts, Open Dashboard, GitHub link, Close) that needs no tab at all. The background now routes the toolbar click by URL scheme: `http(s)://` → the exact previous behaviour (sendMessage toggle, fallback `executeScript` inject); anything else → `chrome.windows.create({ url: float.html, type: "popup", width: 360, height: 680, focused: true })`. If a float popup is already open, the click focuses it instead of opening a duplicate (window id tracked, cleared on `chrome.windows.onRemoved`). An injection failure on an http(s) page also falls back to the popup instead of silently doing nothing. "Add current site" is disabled in the popup with the hint "Open a website to add it" — never a broken button. No `chrome_url_overrides` (the user's new tab page is never replaced), no new permission (see below).
- **FIX (found live, real bug): `chrome.windows.create` bounds ignored under bare Xvfb — `windows.update` enforces the size.** In the live-test environment (Chrome for Testing 158, Xvfb with no window manager) a plain `chrome.windows.create({ type: "popup", width: 400, height: 500, left: 100, top: 80 })` — no extension code at all — still opened at 1280x900, 0,0 (the main window's bounds), and stayed there; a follow-up `chrome.windows.update()` to 360x680 at 920,300 was honoured immediately (proven by a standalone probe, `/tmp/hgf-live-test/probe-windows.cjs`). So `openFloatPopup` now calls `chrome.windows.update({ width: 360, height: 680 })` right after creation and verifies with `chrome.windows.get`, retrying once after 300 ms. Position is deliberately left to Chrome/OS. On a normal desktop both calls agree and the update is a no-op.
- **Permissions unchanged.** `chrome.windows.create` for an extension page needs no extra permission — verified in the built manifest (still exactly `storage, tabs, scripting, activeTab, userScripts, notifications` + optional `*://*/*`; `chrome_url_overrides: None`).
- **Live test (real Chromium, `docs/LIVE_TEST_AUDIT.md` §v1.0.2 addendum): 6 PASS / 0 FAIL** — extensions card 1.0.2, real XTest toolbar click on `chrome://new-tab-page/` opens the 360x680 popup (screenshot `20-float-popup-newtab.png` + desktop shot `20b-desktop-popup.png`), second click focuses it with no duplicate, in-page floating on example.com still opens and drags (regression), and Open Dashboard from the popup opens a normal window while Close closes the popup. ## 1.0.1 — Live-test fixes (2026-11-15)

- **FIX (live test, real bug): `shared/engine.ts` — `world: "ISOLATED"` → `"USER_SCRIPT"`.** `chrome.userScripts.register()` only accepts `MAIN` or `USER_SCRIPT` for the world (`ISOLATED` belongs to `chrome.scripting`, not `userScripts`), so every script install failed with `Value must be one of MAIN, USER_SCRIPT` and nothing ever ran. Found live in real Chrome (registration error shown next to the script in the dashboard + persisted in `hiddengemflow.scripts.errors.v1`); the jsdom smoke tests could not catch it because they mock the API. Docs updated (`README.md`, `docs/AUDIT.md`, this entry).
- **FIX (live test, cosmetic): dashboard favicon 404.** The dashboard page had no favicon link, so Chrome requested `chrome-extension://<id>/favicon.ico` and logged a 404 on every dashboard load. Added `<link rel="icon" href="/icons/icon32.png" />` to `entrypoints/dashboard/index.html`.
- **FIX (live test, real bug #2): scripts registered but never ran — missing host access.** A script registered cleanly (`getScripts()` listed it, no error) yet never executed on a fresh tab. Root cause, verified by experiment: Chrome's `chrome.userScripts` only runs a script where the extension has host access (Chrome docs: add `"host_permissions"` for sites you want to run scripts on) — and this extension requested none. After one real toolbar click on the tab (an `activeTab` grant) + reload, the same script ran. Fix (`wxt.config.ts`, `shared/engine.ts`, dashboard + floating + background): `optional_host_permissions: ["*://*/*"]` (optional, per-site — same trust-first pattern as ScriptSentry; no required host permissions added), a **Grant site access** button on each enabled script in the Scripts tab (Chrome's own prompt, user gesture), a "needs site access" note in the floating window's Active Scripts section, and honest copy in the dashboard + README. Until access is granted, the UI says the script is registered but not running yet.
- **FIX (live test, real bug #3): dashboard showed stale tasks/scripts.** Tasks and scripts were loaded once at startup, so a task saved from the floating window never appeared in the dashboard's Tasks tab (live test: floating saved 1 task, Tasks tab still showed 0 rows) until the page was reloaded; same for a script toggled from the floating window. Fix (`entrypoints/dashboard/main.ts`): `selectTab` now re-reads storage when switching to the Tasks or Scripts tab (same pattern Logs/Scripts already used), plus `chrome.storage.onChanged` listeners for the tasks key and the scripts/errors keys so the lists live-update while the page is open.
- **FIX (live test, real bug #4): floating window's Tasks and Active Scripts sections were stale.** Both sections rendered once at injection and never refreshed, so a script installed in the dashboard (or site access granted for it) never appeared in an already-open floating window — the live test injected the floating, installed a script, granted site access, and the floating still listed no scripts. Fix (`entrypoints/floating.ts`): each section registers its re-run; the refreshers fire when the window is shown again after being hidden and live on `chrome.storage.onChanged` for the tasks/scripts/errors keys. A `chrome.storage` listener is registered once per tab; the bridge banner is unchanged (one-shot by design, dismissal persisted). The first version of this fix still missed the case: the scripts section returned early while "Allow User Scripts" was off, so its refresher was never registered and the section stayed frozen after the toggle was turned on — the early return is removed and `refresh()` now re-checks availability on every run (banner + list heal together). That second-order miss was caught by the same live test (6c2/6e still failed) and re-fixed before the final run.
- Live test (real Chromium, `docs/LIVE_TEST_AUDIT.md`): the store "Load store" flow is correct — it shows the honest "not published yet" message with the 404 detail; the first run only looked stuck because the button stays in "Loading…" while the two fetches run (~2.5s total through this VM's proxy, longer on a cold connection). `chrome.action` toolbar click verified via a real XTest mouse click on the pinned icon (not simulated through the service worker).
- Open (not fixable from code): the Official Store repo `BidyutRoy2/hiddengem-flow-store` exists but is empty — only the owner can publish `index.json` there.

## 0.1.0 — Phase 3: Script Manager (2026-11-15)

- Userscript manager in the dashboard Scripts tab: create (monospace editor, Tab inserts spaces, live metadata), import from `.user.js` file / pasted code / fetched URL, edit with version history (last 10, rollback), enable/disable toggle, backup as one JSON file, merge-restore with confirm, delete with confirm.
- Heuristic security scan before every install (score 0–100, grade A–F; `eval`, `GM_xmlhttpRequest`, `document.cookie`, `unsafeWindow`/`@grant *` high; `innerHTML`, `fetch`/XHR/WebSocket, storage access medium; GM storage low). Scan is a warning, never a block — install needs an explicit Confirm.
- Version upgrade: `Check for update` fetches `@updateURL`/`@downloadURL` (user-triggered), compares versions, shows old → new version + lines changed + scan of the new code, and requires Confirm. No update URL → "Re-import to update".
- `chrome.userScripts` engine (`shared/engine.ts`): scripts registered one at a time in the USER_SCRIPT world with a GM shim for exactly four functions — `GM_setValue`/`GM_getValue` (per-script namespaced localStorage — page-visible, never for secrets), `GM_notification` (real `chrome.notifications` via the background), `GM_addStyle`. Everything else is not implemented and is flagged, never faked.
